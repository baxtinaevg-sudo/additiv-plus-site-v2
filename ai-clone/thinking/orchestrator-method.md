# 🎼 orchestrator-method.md — Метод оркестратора

> Принцип: один планирует, многие делают. Контекст - минимальный.

## Проблема

Когда один агент получает всю задачу целиком:
- Тратятся токены на загрузку ненужного контекста
- Ошибка в начале каскадно размазывается по всей задаче
- Нет специализации: агент делает и ресерч, и код, и тесты

## Модель: Оркестратор + Исполнители

### Роль 1: Оркестратор (планировщик)

Получает на вход:
- Задачу пользователя
- `CLAUDE.md` (карта проекта)
- Структуру папок (через `list_files`)

НЕ получает:
- Исходный код компонентов
- Содержимое data-файлов
- Детали реализации

Делает:
1. Разбивает задачу на микро-задачи (каждая = 1-2 файла)
2. Определяет порядок выполнения
3. Формулирует точный контекст для каждого исполнителя

### Роль 2: Исполнитель (узкий специалист)

Получает на вход:
- Конкретную подзадачу (что сделать, в каком файле)
- Минимальный контекст (только затронутые файлы)
- Правила из `ai-clone/` (только релевантные)

НЕ получает:
- Карту всего проекта
- Задачи других исполнителей
- Необходимость принимать архитектурные решения

Делает:
1. Читает только указанные файлы
2. Выполняет конкретное изменение
3. Возвращает результат

## Структура `ai-clone/` как микро-контексты

Каждый файл в `ai-clone/` спроектирован самодостаточным:

```
ai-clone/
├── thinking/research-first.md    → для исполнителя «перед кодом»
├── thinking/orchestrator-method.md → для оркестратора
├── principles/code.md            → для исполнителя «код»
├── principles/business.md        → для исполнителя «бизнес-логика»
├── voice/stop-words.md           → для исполнителя «контент»
├── feedback/*.md                 → релевантные правила из ошибок
```

Оркестратор говорит: «Прочитай `principles/code.md` и реализуй X в файле Y».
Исполнитель получает 2 файла вместо всего проекта.

## Практические правила

### 1. Правило 3 файлов

Если задача затрагивает > 3 файлов - это кандидат на декомпозицию.

### 2. Правило единственной ответственности

Один исполнитель = одно изменение = один тип работы (код / стиль / данные / архитектура).

### 3. Правило минимального контекста

Загружать в контекст только:
- Файлы, которые нужно изменить
- Файлы, от которых зависят изменения (импорты, типы)
- Одно релевантное правило из `ai-clone/`

### 4. Правило последовательности

Исполнители работают последовательно, не параллельно (в рамках одной задачи).
Результат исполнителя N = часть контекста исполнителя N+1.

## Пример: задача «Добавить обезличивание ПД в CRM»

### Оркестратор разбивает:

1. **Исполнитель «Аналитик»**: прочитать `clients.json`, классифицировать поля (публичные / ПД / коммерческая тайна)
2. **Исполнитель «Код»**: создать `anonymizer.js` с функциями маскировки (контекст: структура clients.json)
3. **Исполнитель «Данные»**: создать `clients.demo.json` - обезличенную копию (контекст: anonymizer.js + clients.json)
4. **Исполнитель «Store»**: обновить `clients.js` для поддержки демо-режима (контекст: anonymizer.js)
5. **Исполнитель «UI»**: добавить плашку демо-режима (контекст: MainLayout.vue)

Каждый исполнитель получил 1-2 файла вместо 15+.

## Экономия токенов

| Подход | Контекст на задачу | Токены |
|--------|--------------------|--------|
| Монолитный | весь проект + все правила | ~50K |
| Оркестратор | карта + 2-3 файла | ~8-15K |
| Экономия | | **3-6x** |
