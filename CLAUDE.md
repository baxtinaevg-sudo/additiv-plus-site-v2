## Что это за проект

**Аддитив Плюс** - российская компания по производству и поставке химических компонентов для строительства и промышленности.
Решает задачи импортозамещения европейских химических добавок собственными брендами с комплексными решениями: от разработки рецептур в лаборатории до техподдержки.

Подробности - `business/INDEX.md`.

## Порядок чтения в начале любой сессии

1. `ai-clone/INDEX.md` - кто я и как думаю.
2. `business/INDEX.md` - что мы делаем (продукт, аудитория, экономика).
3. `CLAUDE.md` (этот файл) - правила репо, стек, навигация.
4. Зона задачи: нужный файл из `business/`, `plans/<актуальный план>`, `mastery/<область>` или папка фичи в коде.

Слой 1 (клон) - раньше слоя 2 (бизнес) не случайно: сначала **кто** думает, потом **о чём**.

## Стек

Vue 3, Vite, Tailwind CSS, Three.js, GSAP, Lenis. Скрипты: Node.js. База знаний: Obsidian (wikilinks). Деплой через GitHub Pages по push в main.

## 8 правил репо

1. **Не хардкодить динамику** (цены, даты, метрики, ID, ссылки). Любые меняющиеся значения - через `business/life-metrics.md` с маркером **LIVE**.
2. **Не деплоить без моей явной команды.** Push в main = автодеплой. Если задача не требует продакшна - не пушь.
3. **Удалять одноразовый код после использования.** Скрипты миграции, отладочные endpoint'ы, временные файлы - убирать в том же коммите, где они отработали.
4. **Перед `git push` - сборка обоих проектов.** Команды: `npm run site:build` и `npm run crm:build`. Не только сборка - проверка, что ничего не сломано. Подробнее см. раздел «Сборка и структура монорепо».
5. **Большая фича = план в `plans/`.** Микрофича - без плана. Граница: если задача больше часа работы - план.
6. **После каждой фичи - цикл из 5 ходов** (см. ниже). Без него фича не считается закрытой.
7. **`git add` поимённо.** Никогда `git add .` или `git add -A`. Параллельно работают другие чаты - их незаконченные правки не должны попасть в коммит.
8. **`.env` только через `grep "^VAR=" .env`.** Никогда не читать целиком - утечёт в транскрипт. То же для файлов с токенами и ключами.

## Большая фича = план в `plans/`

- Один план = одна фича. Если план есть - работаем с ним.
- Имя файла: `YYYY-MM-DD-название-фичи.md`.
- Делится на фазы. Каждая фаза - статус `[ ]` / `[WIP]` / `[x]`.
- По каждой фазе: цель, deliverable, критерий «сделано», задачи.
- В конце плана - итоговый блок: реализовано целиком или нет, что осталось, ссылки на коммиты.
- Любой агент обязан актуализировать план после каждой сессии.

## Цикл из 5 ходов после каждой фичи

Прогоняй каждый раз. Без этого считается, что фича не сдана.

1. **Найди ошибки** в только что написанном коде -> докажи примером -> исправь.
2. **Что упустили** в реализации (граничный кейс, валидация, обработка ошибок) -> докажи.
3. **Это РЕАЛЬНО проблема нашего проекта?** Не выдуманная. Сверь с `business/` и `plans/`.
4. **Свежий взгляд после правок** - перечитай diff, как будто видишь впервые.
5. **Security review.** Опасная тройка: персональные данные пользователей + контент третьих лиц + отправка чего-либо наружу. Если хоть одно - стоп и аудит.

## Любая ошибка -> правило в `ai-clone/feedback/`

Когда я говорю «не так, потому что...» или «больше так не делай» - не запоминай в текущий чат. Оформи как файл в `ai-clone/feedback/` по канону **Rule -> Why -> How to apply**:

- Rule: что конкретно делать или не делать.
- Why: причина, прецедент, какая ошибка была.
- How to apply: в каких ситуациях правило срабатывает.

В следующих сессиях я перечитываю `ai-clone/` первым - правило применится автоматически.

## Динамические цифры -> `business/life-metrics.md`

В файлах `business/` цифры (выручка, конверсии, количество клиентов) не пишутся напрямую - они протухают. Вместо этого:

> Выручка за март: **LIVE** -> `life-metrics.md` / «Выручка за месяц»

В `life-metrics.md` лежит способ получить свежее число. Когда я задаю вопрос про цифры - сначала читай `life-metrics.md`, потом тяни данные, потом отвечай.

## Сборка и структура монорепо

Проект - монорепо: корневой `package.json` + `node_modules/` в корне + два подпроекта.

### Команды сборки (ВСЕГДА из корня)

| Команда | Что делает |
|---|---|
| `npm run site` | Dev-сервер сайта (additiv-plus-site) |
| `npm run site:build` | Production-сборка сайта |
| `npm run crm` | Dev-сервер CRM |
| `npm run crm:build` | Production-сборка CRM |

### Важные правила монорепо

1. **Всегда запускать из корня** - `node_modules/` лежит в корне, подпроекты не имеют своих.
2. **`root: __dirname` в vite.config** - ОБЯЗАТЕЛЬНО для обоих проектов. Без этого vite ищет `index.html` в корне и падает. Не удалять!
3. **Сборка сайта** идёт в `additiv-plus-site/dist/`, CRM - в `crm/dist/`. Обе папки в `.gitignore`.
4. **Docker** (`additiv-plus-site/Dockerfile`) собирает свой `npm ci` + `npm run build` автономно - там `root: __dirname` тоже нужен.
5. **Не создавать** `package.json` в подкаталогах - это ломает hoisting зависимостей.

## Безопасность

### Правила

- **НЕ читать** `.env` и файлы с секретами целиком. Нужна переменная - `grep "^VAR=" .env`.
- **НЕ выполнять** `rm -rf` без моего явного подтверждения. Перед удалением показывай, что будет удалено.
- **НЕ отправлять** переменные окружения, токены, ключи наружу - никаких `curl`/`wget`/POST с этими значениями.
- **НЕ устанавливать** скиллы / MCP / зависимости из непроверенных репо без аудита.
- **НЕ деплоить** без моей явной команды.
- **НЕ коммитить** `dist/`, `node_modules/`, сборочные артефакты - они в `.gitignore`.
- **НЕ коммитить** `crm/src/data/*.json` - там персональные данные (телефоны, email, ИНН). Данные только локально.

### Три уровня .gitignore

1. **Корневой `.gitignore`** - общие правила (секреты, бизнес-данные, dist/, AI-конфиги, amvera-deploy/).
2. **`additiv-plus-site/.gitignore`** - правила сайта (dist/, .env, секреты, данные).
3. **`crm/.gitignore`** - правила CRM (dist/, .env, секреты, `src/data/*.json`).

Все три файла должны быть согласованы. При добавлении нового типа секретных файлов - добавить во все три.

### Что защищено

- `secrets.json` - нигде в git, во всех `.gitignore`
- `.env`, `.env.*` - нигде в git, во всех `.gitignore`
- `crm/src/data/*.json` - данные CRM только локально
- `*.xlsx`, `*.xls` - бизнес-данные
- API-ключи и токены - отсутствуют в коде
